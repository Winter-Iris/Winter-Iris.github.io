- TCP（**传输控制协议**，Transmission Control Protocol）是计算机网络中最核心的协议之一。如果把互联网比作物流系统，IP 协议负责把包裹送到正确的地址
- 而 **TCP 则像是一个极其负责的快递员**：他会确保包裹不丢失、不损坏、且按照发货顺序交到你手里。

# TCP 核心特性

TCP 被称为**面向连接的、可靠的、基于字节流**的传输层协议：
- **面向连接**：在传输数据前，双方必须先建立连接（就像打电话前先拨号）。
- **可靠性**：如果数据在传输中丢失或出错，TCP 会负责重传，确保接收方收到完整正确的数据。
- **有序性**：TCP 会给每个数据包编号，即使网络路径导致包的到达顺序乱了，它也能在接收端按原序组装。
- **流量控制与拥塞控制**：它能根据接收方的处理能力和网络的拥挤程度，动态调整发送速度，防止网络崩溃。

# MSS

**MSS** 的全称是 **Maximum Segment Size**（最大报文段长度）。它是 TCP 协议中一个非常重要的参数，直接影响着数据传输的效率。
简单来说，MSS 是 TCP 报文段中 **“数据部分（Payload）”** 的最大限制，不包括 TCP 首部和 IP 首部。


### MSS 的计算方式

为了理解 MSS，我们需要先看另一个概念：**MTU (Maximum Transmission Unit)**。
- **MTU**：链路层（如以太网）能够传输的最大帧大小，通常是 **1500 字节**。
- **MSS**：在不分片的情况下，TCP 能够发送的最大数据长度。
    
其计算公式通常为：

$$MSS = MTU - IP \text{首部长度} (20 \text{ 字节}) - TCP \text{首部长度} (20 \text{ 字节})$$

如果 MTU 是常见的 1500 字节，那么 **MSS 通常就是 1460 字节**。


### 为什么需要 MSS？（核心作用）

MSS 的存在主要是为了**避免 IP 分片**。
- **分片的风险**：如果一个 TCP 报文加上 IP 首部后超过了链路的 MTU，IP 层就会对其进行分片。分片会增加路由器的负担，且如果其中一个分片丢失，整个 TCP 报文都需要重传，极大降低了效率。
- **TCP 的对策**：TCP 在建立连接时通过协商 MSS，确保发出的每一个报文段在加上 IP/TCP 首部后，依然不会超过链路的 MTU，从而实现“端到端”的完整传输。
    

### MSS 是如何确定的？

MSS 并不是全局统一的，而是由连接双方在**三次握手**期间协商确定的：
1. **SYN 阶段**：客户端在发送第一个 SYN 包时，会在 TCP 选项（Options）字段中写入自己的 MSS 限制（比如 1460）。
2. **SYN+ACK 阶段**：服务器收到后，也会在回传的包中带上自己的 MSS 限制（比如 1400）。
3. **最终取值**：双方会取这两个值中的**较小值**作为本次连接的正式 MSS。

> **注意**：MSS 只限制从一端发送到另一端的数据大小。如果路径中间经过了 MTU 更小的网络（比如某些 VPN 或隧道环境），可能会出现 **MSS Clamping**（MSS 钳制）技术，即路由器在握手阶段强行修改包内的 MSS 值，防止后续包过大导致丢包。



###  MSS vs MTU：

|**特性**|**MTU (最大传输单元)**|**MSS (最大报文段长度)**|
|---|---|---|
|**所属层级**|数据链路层 (L2)|传输层 (L4)|
|**包含内容**|IP首部 + TCP首部 + 数据|**仅数据部分**|
|**典型值**|1500 字节|1460 字节|
|**协商机制**|由网络接口硬件决定|三次握手时双方协商|

### 序列号 (Sequence Number)

TCP 是面向**字节流**的协议。它会给每一个要传输的字节都分配一个唯一的序号。
- **含义**：本报文段所发送的数据的**第一个字节**的序号。
- **作用**：
    - **去重**：如果收到重复的序号，接收方知道这是重传包，直接丢弃。
    - **排序**：数据在网络中可能“抄近路”或“绕远路”，导致到达顺序错乱。接收方根据序列号重新拼装出完整的数据流。
- **初始序列号 (ISN)**：连接建立（握手）时，双方会随机生成一个初始序列号，而不是从 0 开始（为了安全性，防止被伪造包攻击）。

### 确认号 (Acknowledgment Number)

确认号是接收方向发送方反馈状态的机制。
- **含义**：**期望收到对方下一个报文段的数据的第一个字节序号**。
- **计算公式**：确认号 = 已收到的最后一个字节序号 + 1。
- **作用**：
    - **确认收到**：告诉发送方，“到这个序号为止的所有数据，我都安全收到了”。
    - **请求后续**：告诉发送方，“接下来请从这个位置开始发”。

### 累计确认

- **累计确认（Cumulative Acknowledgment）** 是 TCP 提高传输效率的关键机制。
- 它的核心逻辑是：**确认号（Ack Number）不仅代表收到了一个包，还代表“在此序号之前的所有数据都已经安全送达”。**

# 超时处理

- 在 TCP 中，**RTT（Round-Trip Time，往返时间）** 是指一个报文段从发送出去到收到对应的确认号（ACK）所经历的时间。

### RTT 的测量与平滑处理：$EstimatedRTT$

由于单次测得的 RTT（称为 $SampleRTT$）受网络波动影响很大，TCP 采用“加权移动平均”来平滑数据，得到 **$EstimatedRTT$（估计往返时间）**。

$$EstimatedRTT = (1 - \alpha) \times EstimatedRTT + \alpha \times SampleRTT$$

- **$\alpha$ 的典型值**：$0.125$（即 $1/8$）。
- **逻辑**：它给旧的估计值较大的权重，给新的测量值较小的权重，使得 RTT 的变化更加平滑，过滤掉网络瞬时的尖峰。

### 测量波动情况：$DevRTT$

除了平均值，我们还需要知道 RTT 变化的剧烈程度。**$DevRTT$** 用于估算 $SampleRTT$ 偏离 $EstimatedRTT$ 的程度：

$$DevRTT = (1 - \beta) \times DevRTT + \beta \times |SampleRTT - EstimatedRTT|$$

- **$\beta$ 的典型值**：$0.25$（即 $1/4$）。
- **逻辑**：如果网络非常稳定，$DevRTT$ 会很小；如果网络波动剧烈，$DevRTT$ 会变大。

### 计算超时间隔：$RTO$

最后，TCP 根据平滑后的 RTT 和波动情况，计算出最终的 **$RTO$（超时重传时间）**：

$$RTO = EstimatedRTT + 4 \times DevRTT$$

- **为什么乘以 4？** 这是一个经验值。$EstimatedRTT$ 提供了基准，而 $4 \times DevRTT$ 则是预留的“安全边界”。
- **逻辑**：当网络波动大（$DevRTT$ 大）时，RTO 会显著增加，以避免频繁的误重传。


### 指数退避 (Exponential Backoff)

如果发生了超时重传，说明网络可能处于严重的拥塞状态。此时，TCP 不仅会重传数据，还会采取**倍增策略**

- 每连续发生一次超时，就把 RTO **翻倍**（例如：1s -> 2s -> 4s -> 8s...）。
- 一旦收到正常的 ACK，再重新按照上述公式计算 RTO。

这种做法能迅速减少发送端对拥塞网络施加的压力，给路由器“喘息”的时间。


# 快速重传

- **快速重传（Fast Retransmit）** 是 TCP 协议中一种非常高效的丢包补偿机制。
- 它的核心意义在于：**发送方不需要等待“超时计时器（RTO）”到期，就能提前发现丢包并立即重传。**

### 工作原理：三个重复 ACK

快速重传依赖于接收方的**重复确认（Duplicate ACK）**。
当发送方连续发送一批报文段（如 Seg1, Seg2, Seg3, Seg4, Seg5）时，如果中间某个包（比如 Seg2）丢了：

1. **接收方的反应**：
    - 收到 Seg1：回 **Ack=2**（期望收到 Seg2）。
    - 收到 Seg3：发现序号对不上（乱序），**不能**回 Ack=4，必须依然回 **Ack=2**。
    - 收到 Seg4：依然回 **Ack=2**。
    - 收到 Seg5：依然回 **Ack=2**。
2. **发送方的反应**：
    - 发送方收到了第一个 Ack=2（正常确认）。
    - 接着，发送方连续收到了 **3 个重复的 Ack=2**（总共 4 个 Ack=2）。
    - **触发决策**：发送方意识到：“既然对方后面收到了三个包却一直在问我要 Seg2，说明 Seg2 肯定丢了！”
    - **立即行动**：发送方不等计时器超时，直接重传 Seg2。


### 为什么是“3次”重复 ACK？

这是一个经验性的权衡：
- **1 或 2 次重复 ACK**：可能是由于网络路径不同导致的**乱序**（Out-of-Order）。在互联网中，小规模的乱序非常常见，如果立即重传会造成带宽浪费。
- **3 次重复 ACK**：当连续收到 3 个重复 ACK 时，网络发生乱序的概率已经极低，基本上可以判定为**丢包**。

# 流量控制

- **流量控制（Flow Control）** 是 TCP 协议中为了防止发送方发送数据过快，导致接收方缓冲区溢出而采取的一种保护机制。
- 简单来说，它的核心逻辑是：**接收方根据自己的处理能力，动态地告诉发送方“你现在还能发多少数据给我”。**

### 接收窗口 (rwnd)

在 TCP 报文的首部中，有一个 16 位的 **Window Size** 字段。
- **接收方**根据自己当前缓存区的大小，动态计算出一个值，称为 **rwnd (receiver window)**。
- **含义**：接收方告诉发送方：“我目前还能再接收这么多字节，超过这个数我就没地方放了。”

### 持续计时器与窗口探测 (Zero Window Probe)

当窗口变为 0 时，如果不采取行动，可能会进入死锁状态（如果 B 腾出了空间但 A 没收到通知）。
- **窗口探测**：当 A 收到 `rwnd = 0` 时，会启动一个**持续计时器（Persistence Timer）**。
- **探测报文**：计时器到期，A 会发送一个仅包含 1 字节数据的“探测报文段”。
- **强制回复**：B 必须对这个报文回复 ACK，并带上最新的 `rwnd` 值。
    - 如果仍然为 0，A 重置计时器继续等。
    - 如果不为 0，A 重新开始发送。


# 连接管理


## 建立连接：三次握手

连接建立的目的是为了确认：
1. 双方都具有**发送**和**接收**数据的能力。
2. 双方都初始化了**初始序列号 (ISN)**，并对此达成共识。

### 流程拆解：

- **第一次握手：** 客户端发送 `SYN=1`（同步请求），并随机初始化一个序列号 `seq=x`。此时客户端进入 `SYN_SENT` 状态。
    - _潜台词：_ “喂，你能听到吗？我的起始编号是 x。”
- **第二次握手：** 服务器收到后，回复 `SYN=1`, `ACK=1`。它确认了客户端的 `x`（`ack=x+1`），并随机初始化自己的序列号 `seq=y`。此时服务器进入 `SYN_RCVD` 状态。
    - _潜台词：_ “听到了！我的起始编号是 y。我也收到你的 x 了。”
- **第三次握手：** 客户端收到后，发送 `ACK=1`。确认服务器的 `y`（`ack=y+1`）。发送完此报文，客户端进入 `ESTABLISHED` 状态，服务器收到后也进入该状态。
    - _潜台词：_ “太好了，我也收到你的 y 了，咱开始传数据吧！”

- **SYN_SENT**: 客户端发送第一个 `SYN` 后的状态。
- **SYN_RCVD**: 服务器收到 `SYN` 并回传 `SYN+ACK` 后的状态，此时连接处于半开状态。
- **ESTABLISHED**: 双方均已确认对方的序号，可以开始传输数据。

## 两次握手

- 可能会建立半连接（只有服务端在维护的连接）。
- 可能会将老数据当作新数据传输。
如果只有两次握手，可能会出现**失效的连接请求突然传到了服务器**的情况。 
假设客户端发出的第一个 SYN 包在网络中堵塞了，客户端超时重传并完成了连接、传完数据并断开了。过了一会，那个堵塞的 SYN 包到了服务器，服务器以为是新连接，回复 ACK 并开启资源。如果是两次握手，服务器现在就处于“连接已建立”状态，而客户端根本不理它，导致服务器资源白白浪费。

## 释放连接：四次挥手

由于 TCP 连接是**全双工**的（双方都可以同时收发），因此每个方向的连接必须单独关闭。

### 流程拆解：

1. **第一次挥手：** 客户端发送 `FIN=1`（结束标志），表示“我没数据要发了”。客户端进入 `FIN_WAIT_1` 状态。
2. **第二次挥手：** 服务器收到后，回复 `ACK=1`。服务器进入 `CLOSE_WAIT` 状态，客户端收到后进入 `FIN_WAIT_2`。
    - _注意：_ 此时连接处于**半关闭**状态。客户端不能发数据，但服务器如果还有数据没发完，可以继续发。
3. **第三次挥手：** 服务器发完最后的数据，发送 `FIN=1`。服务器进入 `LAST_ACK` 状态。
4. **第四次挥手：** 客户端收到后，回复 `ACK=1`。客户端进入 `TIME_WAIT` 状态，服务器收到 ACK 后立即 `CLOSED`。


- **FIN_WAIT_1**: 主动关闭方发送 `FIN` 后的状态，等待对方的 `ACK`。
- **CLOSE_WAIT**: 被动关闭方收到 `FIN` 后的状态。**注意：** 此时如果程序不调用 `close()`，会一直卡在这里，导致资源泄漏。
- **FIN_WAIT_2**: 主动关闭方收到对方的 `ACK`，等待对方的 `FIN`（即等待对方也决定关闭）。
- **TIME_WAIT**: 核心安全状态。主动关闭方在发送最后一个 `ACK` 后进入，等待 **2MSL** 以确保旧报文在网络中消失，并保证对方收到了最后的 `ACK`。
- **LAST_ACK**: 被动关闭方发送完最后的数据和 `FIN` 后，等待最后一个 `ACK`。

# 拥塞控制

- **TCP 拥塞控制（Congestion Control）** 的目的不是为了保护接收方（那是流量控制的事），而是为了**保护整个互联网**。如果所有用户都全速发送数据，网络中的路由器就会因为缓冲区溢出而大量丢包，导致“拥塞崩溃”。
- TCP 拥塞控制通过维护一个**拥塞窗口**（cwnd, Congestion Window）来**限制发送速率。**
- 发送方实际能发送的数据量（发送窗口）受以下两者共同限制：

$$\text{LastByteSent} - \text{LastByteAcked} \le \min(cwnd, rwnd)$$

- **$cwnd$**：网络能承载多少（拥塞控制）
- **$rwnd$**：接收方能收多少（流量控制）
- **端到端拥塞控制**：
	- 没有来自网络的显式反馈
	- 是否拥塞的判断是由主机根据被观察到的延迟和丢失推测推测出来的
	- TCP采用该方法
- **网络辅助拥塞控制**
	- 路由器在拥塞时，针对途径该路由器的发送方-接收方的数据流，**向这些主机提供直接的拥塞反馈**
	- 可以在反馈信息中指示拥塞的水平和显式指定发送速率

- **拥塞感知信号**：
	- 段的3个冗余ACK: **轻微拥塞**
	- 段超时了（丢失事件）：**拥塞**


### 慢启动 (Slow Start)

当一个 TCP 连接刚建立时，发送方并不知道网络的实时容量。
- **初始状态**：`cwnd` 通常设为一个较小的值（如 1 个 MSS）。
- **增长规则**：每收到一个 ACK 确认报文，`cwnd` 就会增加 1。
- **增长特征**：在一个往返时间（RTT）内，`cwnd` 会呈**指数级增长**（1 -> 2 -> 4 -> 8...）。
- **终止条件**：当 `cwnd` 达到慢启动阈值（`ssthresh`）时，或者发生丢包时，停止慢启动。


### 拥塞避免 (Congestion Avoidance)

一旦 `cwnd` 超过 `ssthresh`，TCP 认为此时已接近网络带宽上限，增长必须变得“谨慎”
- **增长规则**：每收到一个 ACK，只增加 $1/cwnd$。
- **增长特征**：在一个 RTT 内，`cwnd` 仅增加 1，呈现**线性增长**。
- **目的**：通过缓慢探测，寻找网络的最佳平衡点。

#### **慢启动 (Slow Start) 阶段**
在这个阶段，TCP 处于指数增长模式。
- **自循环（new ACK）**：每收到一个新的 ACK，`cwnd = cwnd + MSS`。这意味着每个 RTT 内窗口翻倍。
- **转移到拥塞避免**：当 `cwnd >= ssthresh` 时，进入“拥塞避免”状态，增长速度放缓。
- **检测到丢包（Timeout）**：
    - `ssthresh = cwnd / 2`（窗口减半作为新阈值）。
    - `cwnd = 1`（**彻底回到起点**）。
    - 重传丢失的分组，重新开始慢启动。
- **检测到丢包（dupACKcount == 3）**：
    - 触发“快速重传”，并进入**快速恢复**状态。此时 `ssthresh` 减半，`cwnd = ssthresh + 3`

#### **拥塞避免 (Congestion Avoidance) 阶段**

在这个阶段，TCP 变得“谨慎”，处于线性增长模式。
- **自循环（new ACK）**：`cwnd = cwnd + MSS * (MSS / cwnd)`。也就是每个 RTT 窗口只增加 1 个 MSS。
- **检测到丢包（Timeout）**：处理方式与慢启动相同——**窗口重置为 1**，退回到慢启动状态。
- **检测到丢包（dupACKcount == 3）**：同样进入**快速恢复**状态。
    

#### **快速恢复 (Fast Recovery) 阶段**

这是 TCP Reno 版本的核心，目的是避免不必要的“窗口回 1”。
- **自循环（duplicate ACK）**：每收到一个重复的 ACK，说明虽然丢了一个包，但后续包还到达了接收方，因此 `cwnd` 继续增加 1 个 MSS。
- **转移回拥塞避免（new ACK）**：一旦收到**新的**确认号（说明重传的包被收到了），将 `cwnd` 设为 `ssthresh`（即丢包前的一半），直接开始线性增长。
- **遇到 Timeout**：如果在恢复期又超时了，说明网络极度拥塞，依然要执行“大赦”——`cwnd = 1`，回慢启动。
