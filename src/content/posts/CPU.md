# 流水线

- MIPS 采用 **取指→译码→执行→访存→写回** 五段流水，每段 1 个时钟周期，理想情况下每个时钟周期完成 1 条指令（CPI=1）。

- 通常，一个MPS指令包含如下5个处理步骤： 
	- 1)从指令存储器中读取指令。
	- 2)指令译码的同时读取寄存器。MPS的指令格式允许同时进行指令译码和读寄存器。
	- 3)执行操作或计算地址。
	- 4)从数据存储器中读取操作数。
	- 5)将结果写回寄存器。

| 段 | 缩写 | 主要工作 |
|----|------|---------|
| 取指 | IF | PC→指令存储器取指令, PC+4→NPC |
| 译码 | ID | 字段译码, 读寄存器堆, 立即数符号扩展, 控制信号生成 |
| 执行 | EX | ALU 运算或地址计算, 分支条件判断 |
| 访存 | MEM | Load/Store 访问数据存储器, 分支写入新 PC |
| 写回 | WB | 结果写入目标寄存器（来自 ALU 或存储器） |

![lheZRXTP.png](https://s3.bmp.ovh/2026/05/10/lheZRXTP.png)

- 如果流水线各阶段操作平衡，那么在流水线机器上的指令执行时间为（在理想情况下)：
$$指令执行时间_{流水线}=指令执行时间_{非流水线}/流水线级数$$

# 流水线冒险

## 结构冒险

- **原因：** 硬件资源不足，**导致多个指令在同一周期内竞争使用同一个物理部件。**
- **MIPS的解决方案：**
![uN8owlMe.png](https://s3.bmp.ovh/2026/05/10/uN8owlMe.png)


- **哈佛结构：** 将物理内存分为独立的**指令存储器**和**数据存储器**（或采用独立的一级指令Cache和数据Cache），让取指和访存互不干扰。

![EU5qjGCs.png](https://s3.bmp.ovh/2026/05/10/EU5qjGCs.png)
- 通过流水线停顿避免结构冒险

![z81NffWY.png](https://s3.bmp.ovh/2026/05/10/z81NffWY.png)

- **寄存器堆访问优化：** 为了解决WB（写回）和ID（读寄存器）阶段同时访问寄存器的问题，通常规定**前半周期写、后半周期读**。


## 数据冒险

- **原因：** 指令需要使用前面指令尚未产生或尚未写回的结果。
- **写后读** (RAW, Read After Write)：指令 B 尝试在指令 A 写入数据之前读取该数据。此时指令 B 会读到“旧值”。


- **ALU 型冒险：** 前一条指令是 `add`, `sub` 等计算指令，结果在 **EXE 阶段** 算出，但要到 **WB 阶段** 才写回寄存器。如果紧接着的指令需要用到这个寄存器，就会读错。
![VIhSKRls.png](https://s3.bmp.ovh/2026/05/10/VIhSKRls.png)

- **Load-Use 冒险：** 前一条指令是 `lw`，数据要到 **MEM 阶段** 结束才从内存取出来。如果下一条指令立刻要用这个数据，**即使有转发技术也无法完全消除延迟**，必须暂停一个周期。

![2iHe39OL.png](https://s3.bmp.ovh/2026/05/10/2iHe39OL.png)
### 解决方案

#### 转发/前推

在标准 MIPS 五级流水线中，数据通常在 **EXE 阶段** 结束时由 ALU 算出，或者在 **MEM 阶段** 结束时从内存读出。而下一条指令通常在 **ID 阶段** 读寄存器，**EXE 阶段** 开始计算。
- **EX-EX 转发：** 第一条指令在 EXE 阶段刚算完，结果就在流水线寄存器 $EX/MEM$ 里。此时，第二条指令正好进入 EXE 阶段，转发逻辑直接把这个值接到 ALU 的输入端。
- **MEM-EX 转发：** 第一条指令已经运行到 MEM 阶段，结果在 $MEM/WB$ 寄存器里。此时，第三条指令进入 EXE 阶段，转发逻辑将值传回。

![OObYx93R.png](https://s3.bmp.ovh/2026/05/10/OObYx93R.png)
    
- **优点：** 能够完全消除由于常用运算（如 `add`, `sub`）引起的数据冒险，不损失性能。
- 但是需要硬件逻辑支持：
![RgpcU6HZ.png](https://s3.bmp.ovh/2026/05/10/RgpcU6HZ.png)


#### 阻塞

- **核心思想：** 当转发无法解决问题时（数据还没生产出来），强制让流水线的前端“暂停”，直到数据就绪。
- 转发不是万能的。最典型的例子是 `lw` 指令。
```MIPS
lw  $s0, 0($t1)  # $s0 的值要到 MEM 阶段结束（周期 4）才从内存读出
add $t2, $s0, $t3 # add 必须在 EXE 阶段开始（周期 3）就需要 $s0
```
- 此时只能通过阻塞解决
![x6kGVq5z.png](https://s3.bmp.ovh/2026/05/10/x6kGVq5z.png)

- **硬件检测：** 冒险检测单元发现下一条指令依赖当前 `lw` 指令的目标寄存器。
- **插入气泡 (Bubble)：**
    - **保持 PC 不变：** 防止取下一条指令。
    - **保持 IF/ID 寄存器不变：** 锁定当前正在译码的指令。
    - **清空 ID/EXE 控制信号：** 给执行阶段发一个“全零”信号（相当于执行了一个 NOP），在流水线中形成一个空隙。
- **结果：** `add` 指令被推迟一个周期执行，此时 `lw` 已经完成了 MEM 阶段，数据可以通过转发送给 `add` 了。


## 控制冒险

- **原因：** 指令流水线必须不断取指，但程序流向（下一条指令是谁）往往要等当前指令执行完才知道。
- 即：*尚未确定是否发生分支，不知道如何进行下一次取指*
- **时序矛盾：** 只有当分支指令运行到 **译码阶段 (ID)** 甚至 **执行阶段 (EXE)** 后，CPU 才能计算出是否跳转以及跳转的目标地址。
- 在 CPU 还没确定“跳不跳”的这 1-2 个时钟周期里，流水线已经自动把分支指令后面的指令给取进来了。如果最后发现需要跳转，那这些已经取进来的指令就是“错误指令”，必须被作废。

![gJeS5WAT.png](https://s3.bmp.ovh/2026/05/10/gJeS5WAT.png)


### 解决方案

#### 阻塞

![J2r9KTi8.png](https://s3.bmp.ovh/2026/05/10/J2r9KTi8.png)
这是最简单粗暴的方法。一旦硬件检测到是一条分支指令，就立即暂停取指，直到分支方向确定为止。
- **代价：** 每条分支指令都会造成 1-3 个周期的浪费。由于程序中分支指令非常频繁，这会大幅降低 CPI。

#### 分支预测

- **静态预测：** 永远猜“不跳转”。流水线继续取后续指令。如果猜对了，性能无损；如果猜错了，就把后面取错的指令**清除 (Flush)**，重新到目标地址取指。
- **动态预测：** 硬件内置一个“分支预测表”（BPB），根据这行代码过去跳没跳的历史记录来预测未来。现代 CPU 的预测准确率通常能超过 90%。

#### 假定分支不发生

- “假定分支不发生”（Assume Branch Not Taken）是一种**静态分支预测**策略。它的核心思想是：在流水线取指阶段，不论当前指令是否为分支指令，都默认程序会按顺序执行下一条指令。
- 这种方法之所以能解决控制冒险，是因为它让流水线**不需要停顿**（Stall），而是保持“满载”状态继续运行。
- 如果到 **EXE 阶段**（或提前判定位）发现分支条件为“真”（必须跳转），那么此时流水线里已经取出的后续指令就是错误的，必须立刻清理。
	1. **流水线冲刷 (Pipeline Flush)：** 硬件会向受影响的阶段（通常是 IF 和 ID）发送一个信号，将这些阶段中的指令寄存器内容清零（变成 `NOP` 指令，即空操作）。这就像是“撤回”刚才发出的错误指令。
	2. **更新 PC 指针：** 将 PC 的值修正为分支指令计算出的目标跳转地址。
	3. **重新取指：** 从目标地址开始重新填充流水线。


![bsirHcjo.png](https://s3.bmp.ovh/2026/05/10/bsirHcjo.png)

#### 动态分支预测

- 动态分支预测（Dynamic Branch Prediction）与静态预测（如“假定不发生”）最大的区别在于：它会**根据程序运行的历史记录来“进化”自己的判断**。
- 分支预测缓存 (Branch Prediction Cache)：
	- **BTB (Branch Target Buffer，分支目标缓冲)：**
		- **作用：** 它像是一个“地址导航仪”。
		- **原理：** 当 CPU 取指时，BTB 会记录该指令是否是一个分支指令（如 `jump` 或 `branch`），以及如果跳转成功，**目标地址**在哪里。
		- **效果：** 这样 CPU 还没解码指令，就能直接从 BTB 拿到目标地址开始取下一条。
	- **BHT (Branch History Table，分支历史表)：**
		- **作用：** 它是一个“决策记录本”，专门记录“跳还是不跳”。
		- **原理：** 它通过指令的地址（PC）索引，存储该位置分支的历史状态。

![Z1x0m9f5.png](https://s3.bmp.ovh/2026/05/10/Z1x0m9f5.png)

2 位预测器通常被设计为一个**饱和计数器（Saturation Counter）**，包含以下四个状态：
- **11 (Strongly Taken / 强跳转)：** 极力预测会发生跳转。
- **10 (Weakly Taken / 弱跳转)：** 倾向于预测跳转，但信心不足。
- **01 (Weakly Not Taken / 弱不跳转)：** 倾向于预测不跳转，但信心不足。
- **00 (Strongly Not Taken / 强不跳转)：** 极力预测不会发生跳转。
