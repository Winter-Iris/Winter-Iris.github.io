可靠数据传输(Reliable Data Transfer,简称 RDT)是计算机网络里最经典、也是最优雅的话题之一——它本质上是一个工程问题:**底层信道会出错、会丢包,而我们要在这之上提供一个"假装一切都好"的可靠抽象**。

### 设定问题

应用层希望传输层提供的服务是:**数据按序、无差错、不丢失、不重复地送达**。
但底层网络(IP)只承诺"尽力而为",它可能:
- **比特出错**——电磁干扰让 0 翻成 1
- **分组丢失**——路由器队列溢出、链路中断
- **乱序到达**——多路径路由让后发的先到
- **重复到达**——某些重传机制可能制造副本

RDT 的任务就是用有限的几样工具,把这条不可靠信道"包装"成可靠的。

### 五件工具

整个 RDT 体系其实只用了五样东西,**每一样都精确解决一个具体问题**:

|工具|解决的问题|
|---|---|
|**校验和(Checksum)**|检测分组在传输中是否被改坏|
|**确认(ACK)**|让发送方知道"对方收到了"|
|**序列号(Sequence Number)**|区分新分组和重传的旧分组(避免重复交付)|
|**计时器(Timer)**|检测分组或 ACK 丢失|
|**重传(Retransmission)**|修复丢失或损坏的分组|

# Stop-and-Wait

**停止-等待协议 (Stop-and-Wait)** 是最基础的可靠数据传输协议。它的核心逻辑非常直观：发送方每发送一个数据分组，就必须停下来等待接收方的确认（ACK），只有收到确认后，才能发送下一个分组。

这一协议主要解决了**差错控制**和**流量控制**的问题，它是理解复杂滑动窗口协议（如 TCP）的基石。

## 核心运行流程

该协议主要涉及两个主体：**发送方（Sender）** 和**接收方（Receiver）**。

### A. 理想状态（无差错）

1. **发送**：发送方从应用层获取数据，封装成帧（包含序号 $0$），并启动**定时器**。
2. **等待**：发送方进入等待状态，不再发送新数据。
3. **接收**：接收方收到帧，通过校验和检查无误后，向发送方返回 **ACK 0**。
4. **继续**：发送方收到 ACK 0，停止定时器，发送下一个序号为 $1$ 的帧。


### B. 分组丢失（数据没到）

如果在传输过程中数据分组丢失：
1. 发送方一直等不到 ACK。
2. **超时触发**：定时器到期。
3. **重传**：发送方自动重传刚才那个序号的分组，并重启定时器。
    

### C. 确认丢失（ACK 没到）

如果数据到了，但返回的 ACK 丢了：
1. 发送方超时，重传数据。
2. **重复检测**：接收方根据**序号**发现这个包已经收过了，于是**丢弃该包**，但会**重新发送一个 ACK**（防止发送方陷入死循环）。


# GBN

- **回退 N 步协议（Go-Back-N, GBN）** 是可靠数据传输中的一种“流水线”协议。
- 它的核心思想是：**允许发送方在不等待确认的情况下发送多个分组，但如果出现丢包，就必须“回退”到丢失的地方，重传之后的所有内容。**

### 发送方的三个关键变量

为了管理流水线，发送方维护了一个**滑动窗口**，其大小为 $N$。窗口由以下三个指针界定：
- **`base` (基序号)**：当前窗口中**最早**的未确认分组的序号。
- **`nextseqnum` (下一个序号)**：发送方即将发送的下一个分组的序号。
- **窗口范围**：$[base, base + N - 1]$。在这个范围内的包可以被发送。
- 使用 $k$ 比特序号时，GBN 的最大发送窗口 $W_{max} = 2^k - 1$。

## GBN 的运行流程（事件驱动）

我们可以从发送方和接收方两个视角来看这个“流水线”是如何转动的：

### 发送方响应的事件：

1. **上层调用 (rdt_send)**：
    - 检查窗口是否已满（即 `nextseqnum < base + N`）。
    - **未满**：产生分组并发送，`nextseqnum` 自增。如果这是窗口中第一个发出的包，启动**定时器**。
    - **已满**：拒绝发送数据，告知上层稍后再试。
2. **收到 ACK (rdt_rcv)**：
    - GBN 采用 **累计确认 (Cumulative ACK)**：收到 `ACK n` 表示序号 $n$ **以及之前的所有分组**都已正确接收。
    - **动作**：将 `base` 更新为 $n + 1$。
    - **窗口滑动**：窗口向右移动。如果有仍未确认的分组，重启定时器；如果没有了，停止定时器。
3. **超时 (Timeout)**：
    - **关键点**：发送方只为**最早的那个包**（`base`）维护一个定时器。
    - **动作**：一旦超时，发送方会重传**当前窗口中所有**已发送但未确认的分组（即从 `base` 到 `nextseqnum - 1`）。这就是协议得名“回退 N 步”的原因。

### 接收方响应的事件：

接收方的逻辑非常“死板”且节省内存：
1. **正确收到 $n$ 号包**（且 $n$ 正好是期待的 `expectedseqnum`）：
    - 向应用层交付数据。
    - 发送 `ACK n`。
    - `expectedseqnum` 自增。
2. **收到非期望包（乱序或损坏）**：
    - **直接丢弃**！接收方不会缓存任何乱序到达的分组。
    - **动作**：重新发送**最近一个正确收到包的 ACK**（即 `ACK (expectedseqnum - 1)`）。这实际上是在提醒发送方：“我还在等那个丢了的包呢！”

# SR

- **选择重传协议（Selective Repeat, SR）** 是对 GBN 协议的重大改进。在 GBN 中，一个包的丢失会导致后续所有包被重传（即使它们已经安全到达），这在长距离或高丢包率的网络中非常低效
- SR 协议的核心逻辑是：**“哪坏补哪”**。它允许接收方缓存乱序到达的分组，并要求发送方仅重传真正丢失的那个分组。

- 为了实现“精准重传”，SR 协议引入了以下关键设计：
	- **双端窗口**：发送方和接收方各维护一个窗口。发送窗口控制已发送但未确认的范围；接收窗口控制允许接收并缓存的范围。
	- **独立确认**：接收方对每个正确接收的分组发送**单独的 ACK**，不再使用 GBN 的累计确认逻辑。
	- **独立计时器**：发送方为**每一个**发出的分组都启动一个逻辑上的定时器。
	- **接收方缓存**：接收方能够暂时存放“跳号”的分组（例如收到了 3 和 5，但 4 还没到），直到缺失的分组补齐后再统一交付给上层。
	- 在 SR 协议中，为了避免序号重叠混淆，最大发送窗口 $W_{max} = 2^{k-1}$。

## 详细工作流程

### 发送方事件

1. **从上层接收数据**：检查下一个可用序号是否在发送窗口内。如果在，则装箱发送并为该分组启动专用定时器。
2. **超时**：只有超时的那个分组会被重传。
3. **收到 ACK**：
    - 将该分组标记为“已接收”。
    - 如果收到的 ACK 序号等于窗口的**基序号 (send_base)**，则窗口向右滑动，直到到达第一个未被确认的分组位置。

### B. 接收方事件

1. **收到序号在接收窗口内的分组**：
    - 回传该分组对应的 ACK。
    - 如果该分组之前没收过，则将其**缓存**。
    - 如果收到的分组序号等于接收窗口的**基序号 (rcv_base)**，则将此分组及后续已缓存的连续分组一并交付给上层，窗口向右滑动。
2. **收到已交付的分组 (序号 < rcv_base)**：
    - 必须再次发送该分组的 ACK（这说明发送方没收到之前的 ACK，正在重传）。
3. **其他情况**：忽略该分组。

# 信道利用率计算

信道利用率的通用公式为：

$$U = \frac{N \times t_{trans}}{T_{total}}$$

- 其中 $N$ 是在一个 RTT 周期内可以发送的数据包数量。
- **发送时延 ($t_{trans}$)**：
$$t_{trans} = \frac{L}{C} $$
- 往返传播时延 ($RTT$)
- **一个周期的总时间 ($T_{total}$)**： 从开始发送第一个比特到收到该分组的 ACK
 $$T = t_{trans} + RTT $$
